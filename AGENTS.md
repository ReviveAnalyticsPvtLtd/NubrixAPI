# AGENTS.md

NubrixAI Analytics Hub API — FastAPI + Celery + LangChain monolith.

## Stack
- Python 3.13 (pinned via `.python-version`). Use `uv` for deps; lockfile is `uv.lock`.
- FastAPI on gunicorn (uvicorn worker class), port 7860, mounted at `/api/latest`.
- Celery worker + beat on Redis for billing/subscription/credit/cron jobs.
- LangChain + LangGraph orchestrating LLM components (Gemini via Google GenAI, Groq, Cerebras, OpenAI via OpenRouter).
- Polars as the primary data engine for LLM-generated code (pandas fallback retained for backward compat).
- Supabase (Postgres + Storage), Razorpay billing, Langfuse tracing, Logtail logging.

## Run / Build
- Dev server: `uv run uvicorn main:app --reload --port 7860`. Swagger at `/api/latest/documentation/docs`.
- Production (Docker): `uv sync` then `gunicorn main:app ...` (see `supervisord.conf`). `startup.sh` runs supervisord (fastapi + celery worker + celery beat).
- Single celery task locally: `uv run celery -A nubrix.triggers.celery.celeryApp worker --loglevel=info --concurrency=2`.
- Beat only: `uv run celery -A nubrix.triggers.celery.celeryApp beat --loglevel=info`.

- `nubrix/workflows/` — LangGraph compositions: `reportingToolWorkflow`, `parallelReportingToolWorkflow`. Both have `_route_large_tables_to_scan()` + `_injectProjectId()` + `json.dumps` normalizer post-processors.

## Conventions & Gotchas
- `utils/llm.py:14-16` forces `GOOGLE_GENAI_USE_VERTEXAI=false` and `NO_GCE_CHECK=true` — Gemini always uses the API key path. Don't set `GOOGLE_GENAI_USE_VERTEXAI=true` in `.env` for local runs; the override wins but logs will be confusing.
- CORS is `allow_origins=["*"]` with `allow_credentials=True` (main.py:50). Don't tighten without checking the frontend.
- Auth: JWT HS256 signed with `SECRET_KEY` env var; token must contain `email`. See `api/commons.py:_verifyTokenInternal`. Auth deps are **sync** (not async).
- HTTPException detail can be a `dict` with `status`+`message` — main.py:40 flattens that into the response body instead of wrapping in `{"detail": ...}`. Use `raiseHttpException(...)` / `CustomException` from `utils/exceptionHandler.py` to get the flat shape.
- Celery: beat schedule is in `nubrix/triggers/celery.py` (UTC). All times are UTC. `pastDueSuspension` and `entitlementBoundary` run every 30 min; `reconciliation` every 15 min; `creditReconciliation` hourly; billing/expiry sweeps are daily at 00:00–02:00 UTC. No queue split — single celery worker handles all tasks.
- `pyproject.toml` has no `[tool.pytest]` / lint config and there is no test directory — there are no automated tests. CI is a single GitHub Actions workflow `.github/workflows/subscriptionCron.yaml` that runs `python nubrix/components/subscriptionManager.py` daily. Do not invent a test command.
- `prompts.yaml`, `codeTemplates.yaml`, `config.ini` are loaded by absolute path via `os.path.join(os.getcwd(), ...)` in `CodeGenerator` and friends — run from repo root.
- `.env` is required and gitignored. Required keys: `SECRET_KEY`, `SUPABASE_URL`, `SUPABASE_KEY`, `DATABASE_URL`, `REDIS_HOST/PORT/PASSWORD`, plus provider keys (`GEMINI_API_KEY`/`GOOGLE_API_KEY`, `GROQ_API_KEY`, `CEREBRAS_API_KEY`, `OPENAI_API_KEY`, `LANGSMITH_*`, `LOGTAIL_*`, `RAZORPAY_*`, `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME`, `DASHBOARD_BASE_URL`, `LANGFUSE_*`). The forecast task also needs `FORECAST_DB_USER`, `FORECAST_DB_PASSWORD`, `FORECAST_DB_HOST`, `FORECAST_DB_PORT` and `FORECAST_DB_NAME`; it fails naming any that are missing when it starts, and the app and worker run without them.
- `AGENTS.md` and `CLAUDE.md` are gitignored on purpose — this file is for the local agent, not for git.
- `OPENBLAS_NUM_THREADS=2` is set in `.env` to throttle BLAS (numpy/scipy) in the container.

## Sandbox Execution
- **Code execution** (`utils/codeExecutor.py` + `utils/sandbox_launcher.py`): LLM-generated code runs in a subprocess started by `runSandbox` in `utils/sandboxRunner.py` (`subprocess.Popen` with `close_fds=True`). No fork, no `RLIMIT_AS` (see Run limits), and only the one inherited socket described below. Restricted builtins (`__import__` whitelisted). Timeout via `CODE_EXEC_TIMEOUT_SECONDS` (300 seconds when unset, `0` = none), except the two reporting workflows, which give each generated-code run 35 seconds in code, because a large table's hand-off and a fresh child can take several seconds before the query starts. Soft per-project Redis ZSET semaphore (default 50/project).
- **Transformation execution** (`nubrix/components/transformationExecutor.py` + `utils/transform_launcher.py` + `utils/inspect_launcher.py`): Same subprocess pattern. Child writes parquet to a file in its own folder, and the first 100 rows beside it as JSON, with cells clipped and rows dropped to fit `_MAX_PREVIEW_BYTES`, and stops a result too big to read back. None of that binds generated code, which runs in that process and can write both files itself and exit first, so the parent relies on none of it. Only `_run_transformation` asks `runSandbox` for those files. The parent never decodes a result, because a run can write a file that decodes to far more than the parent can hold, whatever its footer says: it refuses a file over `_MAX_RESULT_BYTES`, checks the parquet frame with `_check_parquet_shape`, which refuses a footer over `_MAX_FOOTER_BYTES` from its 4-byte length, and reads up to `_MAX_PREVIEW_BYTES` of preview as JSON. Keep a preview as rows: rows that each have their own keys make a frame as wide as it is long, which is why `_execute_code` builds nothing. Timeout via `TRANSFORMATION_TIMEOUT_SECONDS` (300 seconds when unset, `0` = none).
- **Project scope**: all three launchers raise `PermissionError` when `fetch_data`, `fetch_data_pl` or `scan_data` names another project. This only gives generated code a clear error. The boundary is in the parent: a child sends a table name over a private socket, and the parent reads that table from the project it started the run for. Never add a project to that protocol. In `transform_launcher.py` and `inspect_launcher.py` the first argument stays named `projectId`, because generated code uses `projectId` and may pass it by keyword.
- **Child environment**: `_INHERITED_ENV` in `sandboxRunner.py` holds only path, locale and tuning variables, plus `SYSTEMROOT`, which sockets need on Windows. A child has no Supabase or Redis settings, and generated code can read everything it does have through `pd.io.common.os.environ`, so never add a secret.
- **Table reads**: `serveTables` runs on a thread while `_runChild` waits, and calls `spool_table` in `initMethods.py`, which reads Redis then Supabase and writes the table to a per-run folder. It only moves bytes, and the child decodes them: a stored table can be the output of generated code. A cold read stays parquet, streamed to disk, and a file up to `_REDIS_MAX_SPOOLED_BYTES` is cached in Redis as it stands. A Redis hit is written out as it stands, as `.parquet` or as an Arrow stream in `.arrow`. `TransformationExecutor.apply` deletes the table's Redis key, so never store a table there. A run stops spooling at `_MAX_SPOOL_BYTES`, and the last table can overshoot it. The parent ends serving with `shutdown` on its own end of the socket, never with anything sent on it, because a child can write to that socket.
- **Separate uid**: each run gets its own uid and group from a range, with no passwd entry, so a child can't read the parent's `/proc/<pid>/environ`, write to `/app`, read `/app/logs` (0700) or reach a run that is going on at the same time. A uid comes round again for other projects, so `_clearUid` runs `sandbox_reaper.py` before and after each run, and the run folder, which is the claim on the uid, stays unless the reaper has cleared what it can find of that uid: processes, files in `work/` and in any shared temp folder still open, and System V objects. A file the uid left in another uid's folder isn't among them, and stays until that folder's owner is cleared. The reaper starts as root and calls `setresuid(spare, run, spare)`, where the spare uid is the run's uid plus `_RUN_UID_COUNT`. Its effective uid is its whole reach, and its real and saved uids put it beyond the reach of anything the run left, which can't signal or trace it. Never let it exec, which would copy the effective uid over the saved one, never give it a real uid of 0, and keep a separate spare uid per run, because reapers sharing a real uid can signal each other. Don't run it by hand as your own uid: it ends every process of the uid it reaches, and it refuses unless started as root. Don't share one sandbox user: concurrent runs for different projects could then read each other's tables and memory. The Dockerfile sets `SANDBOX_RUN_ROOT`, which makes a separate uid mandatory. A root parent without it refuses to run, and so does a non-root parent with it. For local development set `SANDBOX_ALLOW_SAME_UID=1`, which runs children under the developer's own uid, without the limits or the reaper. `test/conftest.py` sets it for tests. The parent needs `CAP_SETUID`, `CAP_SETGID`, `CAP_CHOWN`, `CAP_DAC_OVERRIDE` and `CAP_KILL`.
- **Shared folders**: `_closeSharedFolders` sets `/tmp`, `/var/tmp`, `/dev/shm`, `/dev/mqueue` and `/run/lock` to 0711, and uv's lock files `/app/.venv/.lock` and `/tmp/uv-*.lock` to 0600, whenever a run claims its uid. That leaves a run nowhere to write in the image but its own `work/` and any folder another run has opened to it. uv makes its lock files writable by anyone, and root owns them, so what a run wrote to one would outlive every clear. uv leaves a closed one closed, and the next claim closes any new one. Every clear has to list those folders to find its uid's files, so one run filling one would make every other run's clear time out and lose its uid: a million entries in `/tmp` took 10 to 27 s of a clear's 30. Nothing that uses them here runs as a run uid, and a clear can't list a closed folder, so it costs nothing. A run has no `/dev/shm`, so no POSIX semaphores: joblib warns and runs serially, and a `multiprocessing` lock fails. If one can't be closed the run goes on with a warning in the log, and a clear goes back to paying for a folder. The reaper only enters folders its uid owns, so another uid's tree costs it one entry. What another run left in one of those folders goes when its owner is cleared: any file does, sticky bit or not, and an empty folder does. A folder that isn't empty can't be removed, so the owner's uid stays claimed. In `work/` the parent removes it as root and the next sweep frees the uid. In a shared folder that stayed open it lasts until the container is replaced.
- **Orphaned runs**: a run's worker holds a `flock` on the run folder, which the kernel drops if the worker dies. `sweepOrphanedRuns` runs on a thread when an API worker starts, and clears any folder it can lock: a killed worker leaves processes and copies of customer tables. A worker that dies between API worker starts waits for the next one.
- **Run limits**: `utils/sandboxLimits.py` reads the values below from the environment in the parent each time a run starts (`currentRunLimits`), and the child gets them in the channel dict, never in its environment. An unparsable or negative value falls back to the default and logs a warning. The revert column restores the behaviour from before the limit existed. Every launcher calls `enterSandbox` before generated code runs. On a run uid (Linux, root parent) that sets the hard limits, sets no-new-privileges, installs the seccomp filter and kills the launcher if its worker dies; if any lock-down step fails the child exits before generated code runs. Thread caps and the timeout don't depend on the uid. The slot cap applies only when `SANDBOX_RUN_ROOT` is set, so local same-uid development has no slot cap. With `SANDBOX_ALLOW_SAME_UID=1` there are no kernel limits, no seccomp and no watchdog. The image has no setuid or setgid files. stdout and stderr go to files in the run folder, so nothing a process holds open can block the parent, and it reads at most `_MAX_OUTPUT_BYTES` of each.

  What each one does: `SANDBOX_RUN_THREADS` caps the thread pools of polars, BLAS, numexpr and Arrow. With `SANDBOX_RUN_THREADS=0` the child keeps the parent's `POLARS_MAX_THREADS` and `OPENBLAS_NUM_THREADS`, and `SANDBOX_MAX_RUN_PROCESSES` defaults to 1024 instead of 64, because pools then size from the CPU count and every thread counts as a process; an explicit `SANDBOX_MAX_RUN_PROCESSES` always wins. `SANDBOX_MAX_RUN_PROCESSES` is `RLIMIT_NPROC`. `SANDBOX_MAX_PROCESS_MEMORY_BYTES` is `RLIMIT_DATA`, per process. `SANDBOX_MAX_RUN_MEMORY_BYTES` is the whole run's memory, which the watchdog sums (RssAnon plus RssShmem) over the run uid every 0.1 s. `SANDBOX_OOM_SCORE_ADJ` (0 to 1000; a value outside that range falls back to 1000) puts a run first in line for the kernel's OOM killer, and the watchdog stops a run that lowers it. `SANDBOX_MAX_CPU_SECONDS` is `RLIMIT_CPU`, with a hard limit 10 s above the soft one. `SANDBOX_MAX_DISK_BYTES` and `SANDBOX_MAX_FILES` bound the run's `work/` folder, which the watchdog measures every 1 s. `SANDBOX_MAX_FILE_BYTES` is `RLIMIT_FSIZE`. `SANDBOX_BLOCK_NETWORK` installs a seccomp filter on every thread that refuses network sockets, and also `memfd_create`, `shmget` and `io_uring`, which would let memory sit outside the memory accounting. `SANDBOX_BLOCK_NETWORK=0` lifts all of those refusals, not only the socket ones. `SANDBOX_MAX_CONCURRENT_RUNS` is a container-wide cap on runs at once, held as `flock` slots (`utils/sandboxSlots.py`). A run waits up to `SANDBOX_SLOT_WAIT_SECONDS` for a slot and then raises `SandboxBusyError`, which becomes a 503 `SANDBOX_BUSY` with the copy "Too many analyses are running right now. Please try again in a moment." `REPLManager.run` raises it too, never returns it as output: the report workflows show the copy as that chart's `{"error": ...}` without calling the debugger or rerunning, and the dashboard `getData` (filters and refresh) answers 503 `SANDBOX_BUSY` and saves nothing. On the transformation chat stream the same copy arrives as the assistant message with HTTP 200.

  When a limit ends a run, `SandboxResult.stopped` holds the sentence the user sees: "Execution timed out after N seconds.", "The run was stopped: it used more than N of memory.", "...it wrote more than N to disk.", "...it created more than N files.", "...it changed its own memory priority.", "...it used more than N CPU-seconds.", or "...the server ran out of memory." for a SIGKILL with no other reason.

  History, so nobody re-learns it: `RLIMIT_AS` stays out, because polars reserves far more address space than it uses (VmPeak was 12 GB on a many-core host) and a cap on it broke the import. The old `RLIMIT_CPU` failure was most likely the CPU time of many threads adding up, so the limit is back at 1200 s together with 4 threads. `RLIMIT_DATA` is used together with the thread caps.
- **Run folder**: the child's cwd, `HOME`, `TMPDIR` and result file are in `work/`, which the child owns, so the parent reads the result through `readResult`, which refuses links, pipes and files over the cap. The parent writes tables to `tables/`, which the child can only read. `logger.py` writes `logs/` relative to the cwd, which is why the cwd can't stay `/app`.
- **Stored tables** (`utils/storedTables.py`): a Parquet file can decode to far more memory than its size, so a table a run saved must not be decoded in the API's own process. Every API decode of a stored table goes through one choke point, `decodeStoredTable`, `readStoredTablePage` or `storedTableInfo`, which covers `fetch_data` and its Redis fallback, `dashboardService._getDataTypes`, the data grid, metadata generation (`_attributeInfoFunc`), `reportGenerator` and the profiling report. `test_noOtherStoredTableDecodeRemains` fails on any other decode of stored bytes in `api/`, `nubrix/` or `utils/`. The sandbox child's own `readTable` is the one place that decodes elsewhere, inside the child.
  - **Marker**: the table writers the API owns (CSV, Excel, PDF, SQL and Mongo loads, the dashboard database refresh, and the normaliser) put `nubrix.stored-table` in the file's key-value metadata. Its value is an HMAC of the project and table name, with a key derived from `SUPABASE_KEY`, so a marker is valid only for that table of that project. The parent computes it and a child is only ever handed the value, never the key. A table with a valid marker and a footer of at most 1 MiB is decoded in the worker; any other table (older, no valid marker, a larger or unparsable footer) goes to the reader child. With `SUPABASE_KEY` missing or empty, writers store unmarked tables, nothing counts as marked, and reads stay correct through the reader child; nothing raises. Writers use zstd, 1 MiB pages and 1,048,576-row groups.
  - **Normaliser**: `normaliseRunOutput` rewrites a transformation's output in a trusted run before it is stored. `executeAndPreview` calls it, so the preview, its cache and Apply all hold the normalised bytes (the preview cache key carries a version for that). It streams the input in batches, refuses once the decoded size passes `STORED_TABLE_MAX_DECODED_BYTES`, keeps no metadata except a validated pandas entry, and writes the marker it was given. Validation runs (`_execute_code`) do not normalise. Preview and Apply answer 400 with "The transformation's result is too large to save (over 2 GiB)." or "The transformation's result could not be read safely."
  - **Reader child**: `readUntrustedTable`, `readUntrustedPage` and `readUntrustedInfo` decode an unmarked table in a trusted run whose memory limit is `TABLE_READER_MEMORY_BYTES`, and return Arrow data with dictionary columns decoded to plain values. The answer is capped (the decoded-size limit; 4 MiB for the info answer). A table whose footer says it decodes to more than `STORED_TABLE_MAX_DECODED_BYTES` is refused without being decoded. Cost: every data-grid page, column-type read and metadata read of an unmarked table is one run and holds a slot, so these count against `SANDBOX_MAX_CONCURRENT_RUNS`; a busy sandbox answers 503 `SANDBOX_BUSY`, never "unreadable". Nothing decodes while its own request holds a slot.
  - **Trusted runs**: `runTrustedSandbox` (`utils/sandboxRunner.py`) runs one of our own launchers (`normalise_launcher.py`, `table_reader_launcher.py`) on bytes the parent hands over. It has every limit a code run has (run uid, kernel limits, seccomp, watchdog, slot), serves no tables, and carries no secret: the `request` dict holds only values such as the marker and the limits. The answer is the `work/result` file, read through `readResult` up to a cap.
  - **Writers**: `writeStoredTable` and `writeStoredTableToPath` refuse a table over `STORED_TABLE_MAX_DECODED_BYTES`: 413 `TABLE_TOO_LARGE`, "This table is too large to load (over 2 GiB)." The load gives its name claims back and keeps tables it already stored.
  - **Refusals on reads**: 413 `TABLE_TOO_LARGE`, "This table is too large to open (over 2 GiB)."; 422 `TABLE_UNREADABLE`, "This table could not be read safely." Any `except` around a decode lets those and the 503 pass unchanged (`tableReadException`). `getAllColumns`, `generateMetadata` and `generateReport` run off the event loop (`asyncio.to_thread`), because their reader runs can wait for a slot.
  - **Reverting**: `STORED_TABLE_NORMALISE=0` stores a run's output as it is, with no marker, and also stops trusting markers, so every read of every table, including ones the API wrote, goes to the reader child and holds a slot. `STORED_TABLE_MAX_DECODED_BYTES=0` turns the size checks off; a reader answer is then capped at the larger of `TABLE_READER_MEMORY_BYTES` and 2 GiB. `TABLE_READER_MEMORY_BYTES=0` decodes an unmarked table in the worker, with no child and no slot; the data grid then downloads such a table whole instead of reading it by ranges. Each switch works alone. The setting closest to the behaviour before bounded reads is `STORED_TABLE_NORMALISE=0` together with `TABLE_READER_MEMORY_BYTES=0`. The values are in the Run limits table.
- **Still open**: with `SANDBOX_BLOCK_NETWORK=0` a child can reach any host, and in either case it holds no credentials, only its own project's data. A run's own tree of millions of files can time out its own clear, which keeps that uid claimed until a sweep gets through it. Also open:
  - A marked table is decoded in the API worker, bounded by `STORED_TABLE_MAX_DECODED_BYTES` and not by a memory limit, so several large reads at once still add up in one worker.
  - Blocked event loop: the sandbox calls are synchronous, so a run, and now a slot wait of up to 120 s, can block the event loop in the async approve, apply and rollback paths of `transformationService`. Approve now makes two runs (the run and the normaliser). The async load handlers in `dataLoadService` also generate metadata on the event loop; a freshly loaded table is marked, so that needs no reader run, except with `STORED_TABLE_NORMALISE=0` or no `SUPABASE_KEY`. Moving those onto a thread is a follow-up.
  - Watchdog sampling: memory is sampled every 0.1 s and `work/` every 1 s, so a run can pass a limit briefly before it is stopped. The watchdog measures `work/` once a second; a container-level disk cap is a follow-up.
  - A `ProcessPoolExecutor` that forks without exec (`managementService`; the dashboard re-runs use threads) can keep a slot's file descriptor until its pool ends. Reader runs from other requests make a held slot at fork time more likely; it is not a deadlock, the pool's own runs just skip that slot.
  - A dashboard database refresh refused with 413 on a later table keeps the tables it already uploaded, but their shapes and caches are only updated by the next successful refresh.
  - Slot waiting polls. It has no queue, so waiters have no order.
  - If the watchdog itself crashes it stops the run with the "ran out of memory" sentence.
- **Why subprocess not fork**: Fork inherits parent's open Redis/HTTP sockets → deadlock when child uses `fetch_data_pl`. `close_fds=True` in `Popen` prevents this.

## Data Layer (`utils/initMethods.py`)
- `fetch_data(projectId, table)` → `pd.DataFrame` (backward compat).
- `fetch_data_pl(projectId, table)` → `pl.DataFrame` (eager, zero-copy from Arrow cache).
- `scan_data(projectId, table)` → `pl.LazyFrame` (predicate/projection pushdown).
- Arrow LRU cache bounded by `DF_CACHE_MAX_BYTES` + `DF_CACHE_MAX_ENTRIES`.
- `classify_table_size(projectId, table)` → `{rows_estimate, columns, size_class, hint}`. Drives workflow auto-routing.
- `serializer` — converts Polars types for `json.dumps`.
- `invalidate_data_cache(projectId, table)` — call after transformations.
- Every AnalyticsHub read goes through `utils/projectStorage.py` with the service key, in the API and Celery. Sandboxes have no key, so `use_table_source` sends their reads to the parent. Its sync reads raise `StorageReadError` for a bad status or a bad Range answer, because `httpx.HTTPStatusError` can't be unpickled and breaks a `ProcessPoolExecutor`. Transport errors such as `httpx.ConnectError` stay httpx types, which do pickle. The async reads in `reportingService.py` and `transformationService.py` keep `raise_for_status`. Never add a read through a public URL: `test_storage_read_paths.py` fails on `FILE_URL` and on stray `urlopen` calls. `DOMAIN_FILE_URL` is a separate public bucket.

## Table Viewer Endpoint
- `GET /api/latest/projects/viewTable/{projectId}/{tableName}?page=1&pageSize=100`
- Uses `readTablePage` (`utils/projectStorage.py`), which calls `readStoredTablePage` (`utils/storedTables.py`). For a marked table that reads by ranges through `openTableFile`: an authenticated HEAD for the size, then Range GETs for the parquet footer and the row groups holding the page, decoded batch by batch up to the end of the page.
- An unmarked (older) table is not read by ranges: it is downloaded whole and read by the reader child, so each page costs a download and one run with a slot. The same holds for its column-type read and metadata read. A table over the decoded-size limit answers 413 `TABLE_TOO_LARGE`, an unreadable one 422 `TABLE_UNREADABLE`, and a full sandbox 503 `SANDBOX_BUSY`.
- Keep the HEAD. On the local file backend a one byte Range GET took 500 ms on a 280 MB object, against 9 ms for HEAD, so a Range GET for the size is only the fallback when an edge drops `Content-Length`.
- Tables written with pandas are often one row group, so the whole group's bytes are fetched but must not be decoded whole. Keep `iter_batches` here, not `read_row_groups`.
- Do not go back to `pl.scan_parquet` here. Polars 1.42 silently drops `storage_options` on HTTP URLs, and a signed URL makes storage read the whole object on Polars' HEAD.
- Auth via `verifyToken`. Max page size 500.

## Active/Inactive Tables
- Every table in `metadata.json` has an `isActive` boolean. Missing key = active (backward compat).
- `PATCH /api/latest/projects/toggleTableActive/{projectId}/{tableName}` — toggles `isActive`, persists to storage. Auth via `verifyToken`.
- `managementService.filterActiveTables(metadata)` — shared helper, returns only active entries. All LLM-facing consumers use it:
  - `reportingService._getProjectMetadata` (filters on return, caches full metadata)
  - `transformationService._get_metadata` (same pattern)
  - `managementService._generateRawInsights` (filters before LLM)
  - `blendService.getDataSources` / `getFieldsFromSources` (raw tables only)
  - `reportGenerator.getAllTables` (only active tables)
  - `insightContextBuilder.build` (filters metadata)
- Dashboard re-runs (`getData` with filters or refresh) deliberately ignore `isActive`: saved Python and ChartRequest widgets keep reading inactive tables. `dashboardService._rerunTables` passes every metadata table to the SQL check (active ones first, then inactive, each in metadata order, so a name that differs only in case resolves to the active table), or the stored `<table>.parquet` files, sorted, when metadata.json can't be read. Only new chart generation is limited to active tables. Don't switch it to `filterActiveTables`.
- `getMetadata` endpoint returns ALL tables with `isActive` flag (frontend shows active/inactive status).
- New tables get `isActive: true` automatically. Metadata regeneration preserves existing `isActive` for unchanged tables.

## Table Name Collision Guard
- `managementService.validateTableNameAvailable(projectId, tableName)` — raises `409` if name exists in metadata (active or inactive).
- Called at every table creation entry point: CSV/Excel/PDF/MySQL/PostgreSQL/MongoDB load, through `dataLoadService._acceptTableName`, which also clears any transformation artifact naming that table, and again once the file is written.
- Transformation: `_validate_transformation_table_name` runs at create, rename and approve, and again straight before apply and rollback write the table (`_claim_table_name`: check, claim in `latest_approved_artifact`, check again). A table file the transformation did not write is refused, with or without a metadata key.

## Quick orientation for new tasks
- New HTTP endpoint: add a function to the relevant `api/routers/*.py` (or a new router + `app.include_router` in `main.py:77-88`), put logic in `api/services/`, secure with `Depends(verifyUser)` or stronger dep from `api/commons.py`.
- New LLM component: copy the pattern in `nubrix/components/codeGenerator.py` — load `prompts.yaml` and `config.ini` via `nubrix.utils`, get the model via `utils/llm.getGenaiLlm`, post-process with `cleanThinkTokens` if the model emits ` iNdEx` blocks. Or use `buildLlmChain(section, promptKey)` from `llmChainFactory.py`.
- New scheduled job: implement class in `nubrix/triggers/tasks/`, wire into `celery.py` (task decorator + beat entry), import at top of that file.
- New table creation entry point: call `managementService.validateTableNameAvailable(projectId, tableName)` before upload to prevent name collisions.
- Don't add: async auth deps, tenant concurrency caps, Celery queue splits, proxy clients, session caching, rollups, Docker cgroup tweaks. These were tried and reverted — see MEMORY.md. The sandbox slot cap (`SANDBOX_MAX_CONCURRENT_RUNS`) is the exception, added because of a measurement: reports start 16 runs at once and the dashboard 4, while the container's process limit is lower than that many runs at their thread count.
